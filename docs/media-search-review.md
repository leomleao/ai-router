## Contract boundary

The [subscription preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) are the authority for the OpenAI subscription route, not API-credit or general paid API availability. It requires HTTP Responses requests to set `store:false` and `stream:true`, send the full `input` history on every request, and omit explicit system-role message items. It lists text, images, and files as supported when the selected model accepts them, while audio/video, Files upload API, and transcription are unsupported. Web search remains subject to selected-model and account/workspace policy; image generation, file search, Code Interpreter, hosted MCP/connectors, native computer use, and `tool_search` are explicitly unsupported on that route. This supports a gated Responses `web_search` attempt, not a claim that every subscription, model, or workspace can use it.

For the public API media shapes, the router should intentionally implement a bounded subset:

| Input | Documented public API shape | Approved router subset and current snapshot |
| --- | --- | --- |
| Chat image | `messages[].content[] = {type:"image_url", image_url:{url, detail?}}`; `url` may be HTTPS or a base64 data URL; detail is `auto`, `low`, or `high`. | Accept PNG/JPEG/WEBP/non-animated GIF only, base64 data URLs or HTTPS URLs, preserve detail for OpenAI; router cap 768 KiB decoded per inline image, 8 images/request, and the existing 1 MiB inbound body cap. `src/media.rs:67-100`; `src/protocol.rs:503-514`. |
| Responses image | `input[].content[] = {type:"input_image", image_url:<URL-or-data-URL>, detail?}`; the general API also documents uploaded image `file_id`. | Accept URL/data URL plus detail; do not accept IDs or use Files API. Same router caps. `src/media.rs:86-100`. |
| Responses document | `input_file` with exactly one `file_data` plus a `filename`, or `file_url`; general API also documents `file_id`. | PDF only for inline `data:application/pdf;base64,...`; accept HTTPS `file_url`; reject IDs, local paths, non-PDF, and `filename` with URL. Current cap is 768 KiB decoded and one file/request, below the documented general API 50 MiB combined file cap. `src/media.rs:102-136,179-183`; `src/protocol.rs:672-680`. |
| Chat document | Chat Completions documents a `file` content part with `file_data` and filename for PDF only; it does not document `file_url`. | Current parser does not accept the Chat `file` part, only Responses `input_file`. Decide whether this is intentionally Responses-only and document that boundary, or add the PDF-only Chat shape; add a regression either way. |

The general image API documents PNG, JPEG, WEBP, and non-animated GIF, up to 512 MB total and 1,500 images/request. These are upstream ceilings, not safe router limits. Keep the router's much smaller byte, body, and image-count limits and fail locally before provider I/O. The file guide documents wider Responses file types, but the approved router subset is PDF only; do not silently expand MIME types based on paid API docs. ([Images and vision](https://developers.openai.com/api/docs/guides/images-vision), [File inputs](https://developers.openai.com/api/docs/guides/file-inputs))

### URL and file handling risks

- Keep the current no-download rule. `https_url` checks scheme, host, userinfo, and fragment (`src/media.rs:182-187`) but forwards arbitrary public HTTPS hosts and IP literals to the upstream. The router does not SSRF-fetch these URLs; nevertheless, treat remote URL fetch as upstream behavior, reject credentials/fragments and non-HTTPS before queueing, and never log or persist full URLs, signed query strings, or filenames. Test `localhost`, private/link-local IPv4 and IPv6 literals, unusual ports, encoded userinfo, Unicode hosts, redirects as seen by upstream, and query-string tokens. Do not add router DNS resolution/download as a workaround.
- `file_url` has no filename and is only valid on Responses; `file_data` must carry a safe basename. Keep traversal, control characters, slash/backslash, oversized names, empty names, conflicting fields, missing filename, path inputs, and uploaded IDs as negative fixtures.
- The HTTP limit applies to the full JSON/multipart request, including base64 expansion, history, JSON syntax, and prompt. A 768 KiB decoded payload becomes about 1 MiB base64 by itself; the actual request may exceed the existing 1 MiB cap. Ensure oversize errors are clear and happen before queue/provider work; do not advertise 768 KiB as an always-usable payload size.

## Media validation and routing findings

1. **High — provider fallback must be capability-gated before admission.** `generate_body` chooses a fallback before request normalization (`src/api.rs:999-1019`) and then normalizes, with no use of `RunRequest::has_media` before provider admission (`src/protocol.rs:303-326`, `src/api.rs:1072-1125`). AGY's serializer does reject files and remote image URLs (`src/media.rs:152-168`), but that is a late adapter failure, and images may be locally serializable while the serving account/model lacks image capability. Reject media for any crossed fallback or incapable selected provider/model before admission and dispatch, with an explicit unsupported error; preserve text-only fallback. Cover OpenAI file→AGY, OpenAI HTTPS image→AGY, and OpenAI inline image→AGY when that exact model is not media-capable. Never silently discard media or switch to another paid provider.
2. **High — image format checks are signatures, not full decoders.** `verify_image` (`src/media.rs:145-176`) checks PNG prefix plus substring absence of `acTL`, JPEG start/end bytes, WEBP markers plus the literal sequence `VP8X\x02`, and a small GIF frame walker. These checks can accept malformed/truncated image structures; the WEBP test is not a reliable animation detector (animation is signaled by VP8X feature flags/chunks), and substring checks can both false-positive and miss structural cases. A short header also says nothing about pixel dimensions/decompression cost. Prefer a real bounded decoder/parser that validates container structure, non-animation, dimensions/pixel count, and decoded resource limits before dispatch; otherwise narrow the documented promise and add crafted malformed/APNG/animated-WEBP/GIF/JPEG fixtures. Keep byte/count limits in addition to decode limits.
3. **Medium — PDF validation is only a prefix check.** `normalize_pdf_data` verifies the data URL MIME and `%PDF-` prefix (`src/media.rs:179-183`) but not a complete or sane PDF. That is sufficient only as a type hint, not a validated-document claim. Keep upstream rejection safe and bounded; add synthetic truncated/invalid PDF cases and avoid parsing/rasterizing PDFs in the router.
4. **Medium — text-only multipart content may have changed semantics.** `openai_content` concatenates text blocks without separators when no media is present (`src/media.rs:182-196`); the previous OpenAI `content_text` path joined array-part text with newlines (`src/openai.rs` pre-change serializer around 796). This can turn `[{type:"text",text:"a"},{type:"text",text:"b"}]` from `a\nb` into `ab`. Add a text-only Chat and Responses regression to preserve old behavior, including mixed text/image order.
5. **Medium — Chat file input is an API compatibility decision.** The official file guide says Chat Completions accepts only PDF file parts (`type:"file", file:{filename,file_data}`), while Responses accepts `input_file` including `file_url`; current `normalize_content` only handles Responses `input_file` (`src/media.rs:102-136`). Make the chosen endpoint support explicit; if adding Chat PDF, test both request serialization and tool-turn replay.
6. **Media limits need to be tested as request-wide, not message-local.** Protocol currently accumulates image counts across Chat messages and Responses items (`src/protocol.rs:509-514,672-680`) and caps files at one. Keep tests for 8 vs 9 images spread across multiple turns, 1 vs 2 PDFs spread across turns, mixed inline/URL images, and history near 1 MiB. The Responses path sends up to the same overall 8-image cap even though upstream allows far more; that is intentional.

Inline base64 checks currently require standard padded-base64-compatible decoding, a canonical `data:<exact-mime>;base64,` header, non-empty bytes, and the 768 KiB cap (`src/media.rs:185-210`). Test malformed commas/parameters, whitespace, URL-safe alphabet, invalid padding, wrong MIME/signature pairs, empty payloads, payload at and over the cap, and canonical re-encoding into CCA `inlineData`. The AGY projection only emits inline bytes and rejects HTTPS image URLs and all OpenAI files (`src/media.rs:148-168`); do not infer URL support from Gemini API shapes without verifying the exact CCA request contract.

## OpenAI web search contract

- For Responses, the native request is `tools:[{type:"web_search"}]`; the model may choose whether to search. The HTTP subscription route still requires `stream:true`, `store:false`, array `input`, and no explicit system-role item. Search configuration/selection is distinct from client functions. If the client also defines functions, retain them as a separate custom-tool catalogue; never return a `web_search_call` as a client `function_call` or hand hosted search execution to the client.
- Nonstreaming Responses output includes `web_search_call` items (`id`, status, action such as `search`, `open_page`, or `find_in_page`) and a `message.content[].annotations[]` array. Preserve the original item order and full bounded item shape; preserve each `url_citation` with URL, title, and start/end indices. The docs require cited URLs to be visible and clickable to end users. If using `include`, the documented values include `web_search_call.action.sources` and `web_search_call.results`; do not pass through arbitrary includes unsupported by subscription policy.
- Responses stream mode must preserve search call `response.output_item.added/done` and annotation events such as `response.output_text.annotation.added`, alongside output text deltas and terminal response. `response.completed` can carry the final complete response; correlate item/content/annotation indices and test citations arriving after the related text delta. Do not represent search progress events as function arguments. The router currently always streams upstream, so its Chat and Responses nonstreaming paths still depend on correctly rebuilding complete public objects from that stream.
- Chat web search is a separate specialized integration: the documented request is Chat Completions `web_search_options:{}` with the search model `gpt-5-search-api`; it always searches, whereas Responses lets the model decide. Nonstreaming citations are in `choices[].message.annotations[]` as `type:"url_citation"` with nested `{url,title,start_index,end_index}`; return them in the Chat message and retain indices against the exact returned text. In Chat streaming, preserve any citation annotations on chunks/final chunk and expose a final response message whose annotations match nonstreaming; add official SDK coverage. Do not send `web_search_options` on arbitrary catalogue model IDs as though hosted Responses `web_search` and Chat search model selection were interchangeable.
- Subscription docs say web search is subject to account/workspace policy. An upstream rejection must become a clean public error and metadata-only log, not be rewritten as a custom function call or trigger provider/model fallback. No live subscription eligibility or search call was tested.

## OMP pinned-source observations

- `packages/ai/src/providers/google-shared.ts:59-66` maps `ImageContent` URL directly to Gemini `fileData.fileUri`; inline data maps to `inlineData`. That is useful provenance but does not by itself verify CCA's accepted remote URL form. The router currently rejects remote image URLs for AGY.
- **Do not port OMP's image model/origin fallback.** `packages/ai/src/images/google-antigravity.ts:35-58` falls back to `model.requestModelId ?? model.id` when image-model discovery returns none and returns configured, primary, and sandbox endpoints as candidates. Lines 130-174 retry other origins on 429/5xx. Approved scope instead requires a currently advertised image ID and one verified advertised origin; absent discovery must fail before image dispatch and generation must never be auto-retried. This urgent issue was sent to the coordinator as a status message.
- The OMP endpoint candidate helper deduplicates strings but makes no claim that the account advertised every origin; do not carry its endpoint loop into router execution. Keep auth/account-generation pinning and cancellation from the router's existing provider lifecycle.

## Privacy, telemetry, and HTTP image route requirements

Current request captures are bounded and memory-only; durable telemetry is metadata-only (`src/api.rs:892-923`, `src/monitor/payload.rs:22-49`). The current capture redactor strips data URLs, `file_data`, `b64_json`, and nested `inlineData.data` before shortening strings (`src/monitor/payload.rs:77-148`). Preserve this ordering so large binary strings never consume capture budget. Add fixtures for exact public `image_url`/`input_image`, `file_url`, prompt, filename, citations, raw base64, nested provider parts, and generated `b64_json`; assert the capture retains only useful shape/size metadata and none of the media bytes. Also prove none of these values enters structured logs, telemetry disk records, errors, or API serialization. URLs/filenames/prompts/citations may be visible in the protected in-memory monitor capture only if that remains consistent with the approved capture policy; never persist them.

For `/v1/images/generations`, test JSON `model`, `prompt`, `n`, `size`, and `response_format`; only return supported `b64_json` data with a bounded complete image and MIME type. For `/v1/images/edits`, test real multipart parsing with `model`, `prompt`, repeated `image` fields (including n8n client field naming), filename/MIME validation, request-bound enforcement, cancellation, malformed boundaries, and no local temporary-file persistence. Reject unsupported mask/quality/background/style/output-compression/URL fields explicitly unless implemented. Keep generation count and total response bytes bounded. Route selection must use only the serving account's currently advertised image model ID; no model guessing, alternate origin, provider fallback, or paid retry. The route must share standard key authentication, provider-specific admission, deadline, cancellation, readiness/account-generation checks, and metadata-only telemetry.

The general OpenAI image guide is only a compatibility reference for standard fields and formats, not evidence that ChatGPT subscription usage includes image generation; subscription limitations explicitly disable image generation. See [image generation API guide](https://developers.openai.com/api/docs/guides/image-generation) and the subscription page above.

## Coordinator closure and scope clarification

This is a historical review snapshot; the unchecked list above records requested
checks, not final results. The final implementation expands inline Responses
files to the explicit PDF/TXT/CSV/JSON/DOCX/PPTX/XLSX subset and supports Chat PDF
parts. Its Chat search extension translates to upstream Responses, rather than
using the separate paid Chat search endpoint or specialized Chat search models.
See [the current guide](media-search.md) for the final contract.

Routing rejects cross-provider media fallback, AGY files/remote images/search,
and models without exact advertised AGY vision support before admission.
Bounded image container parsers replace signature-only validation; they enforce
structure, dimensions and non-animation without fully decoding compressed image
pixels. Document signature hints are explicitly narrower than full validation.
Private capture tests redact binary before truncation; persisted telemetry
remains metadata only. Search-source and citation rendering, tool-choice
semantics and SDK contracts are covered by the combined regression suite.
Final test results and remaining live-account acceptance are recorded in
[validation](validation.md).

# Capabilities

This is a model-only router. `/v1/capabilities` reports schema version 3 and
the current direct Antigravity and OpenAI provider readiness. Contract fixtures
exercise local serialization and decoding. Local Google sign-in and exact-ID
discovery succeeded; Flash High, Opus Medium and Sonnet High passed live text,
streaming, JSON and client-tool round trips through both APIs. Argon Medium
returned upstream quota errors. Matched CLI latency and real token refresh
remain acceptance gates; see [validation](validation.md).

| Feature | Current behavior |
| --- | --- |
| Provider routing | Exact discovered model IDs map to one provider and are never remapped. Conflicting IDs are withheld. There is no account fallback, and a known model whose provider is unavailable is never rerouted. Ownership of every served ID (at most 4,096, oldest forgotten first) is persisted to `known-models.json` in the telemetry directory, so it survives restarts; a missing or corrupt file starts empty and is rewritten. |
| Model fallback | A requested chat model ID the router has never served (not live, conflicting, or remembered, and not a fallback target itself) is served by a configured exact target instead of returning `model_not_found`. IDs starting with `gemini` (any case) use `AI_ROUTER_FALLBACK_GEMINI_MODEL` (default `gemini-3.8-flash-medium`); all others, including `gpt-*`, `o*`, codex and `claude-*`, use `AI_ROUTER_FALLBACK_OPENAI_MODEL` (default `gpt-6-luna`). If that target is not in the live catalogue, the other target is used when it is live. If neither is live, the first remembered target is still selected, so the client gets its real availability error (503 or 429, with retry guidance) and the fallback header; `model_not_found` is returned only when neither target has ever been seen. A target ID requested directly, or any remembered ID, is never cross-served, even after a restart during its provider's outage; a target that no catalogue has published yet (a first start during that outage) returns `503 provider_unavailable` with `retry-after`. Deliberate exceptions to the fallback rule return `400 model_not_found`: IDs that are not valid catalogue identifiers (empty, over 128 bytes, or containing characters other than letters, digits, `.`, `:`, `_` and `-`), and non-chat model families (`text-embedding-*`, `dall-e*`, `gpt-image*`, `whisper*`, `tts-*`, `omni-moderation*`, and IDs with a `transcribe`, `realtime`, `audio` or `tts` segment), whose message says the router serves chat models only. A misdirected embedding, image, audio or moderation client therefore gets a configuration error instead of paid chat output. Every affected response, including errors, carries `X-AI-Router-Model-Fallback: <requested> -> <served>`; in the requested ID, any other character becomes `_`, and an ID cut at 128 characters ends in `;truncated`. Response bodies report the served ID, and reasoning effort is then decided for the served model (see Reasoning controls). `/v1/models` lists only real catalogue IDs. `AI_ROUTER_MODEL_FALLBACK=false` restores strict exact-ID behaviour. A crossed fallback (served by the second target because the first is down) cannot carry reasoning state between providers: a Responses request that replays reasoning (inline, or by `item_reference` to a stored reasoning item) while crossed to Antigravity returns `503 provider_unavailable` with `retry-after`, instead of a 400. A conversation whose earlier turns were served by the crossed target and that later returns to its usual target cannot reference that target's reasoning either; resend full history or start a new conversation then. |
| Readiness | Catalogues are usable only while their provider is enabled, authenticated, and checked within 180 seconds. Account generation and persistent restrictions are checked at admission and before dispatch. |
| Antigravity | Direct Rust HTTP/SSE adapter using a fixed reviewed origin, pinned identity, and reviewed protocol baseline. Text generation, history, client tools, and validated JSON are in scope. |
| OpenAI | Independent opt-in Responses adapter. `AI_ROUTER_OPENAI_ENABLED` defaults to false; OpenAI state and admission are separate from Antigravity. |
| Client tools | The gateway validates tool names, object arguments, and the full JSON Schema before returning calls to the client. The client runs tools and sends results in later history. The gateway never executes client tools. |
| Noncompliant tool calls | With `tool_choice` absent or `auto`, a provider call that fails validation only because it names an undeclared tool (while no declared tool is `strict: true`), or because its object arguments do not match a non-strict tool's schema, is returned to the client unchanged, as OpenAI returns such calls for non-strict tools. This is what agent clients rely on to recover: Twenty's agent declares `learn_tools`/`execute_tool`, and when the model calls a learned tool directly, Twenty answers with a tool error that steers it to `execute_tool`, or repairs invalid arguments; previously the router failed those turns with `502 invalid_provider_tool_call`. The undeclared call and its result replay in later history. Calls to a `strict: true` tool, any call under `none`, `required`, a named or an `allowed_tools` choice, malformed names, non-object or invalid-JSON arguments, duplicate call IDs and incomplete calls still fail closed with `502 invalid_provider_tool_call` (`x-should-retry: false`). Each relayed call is logged as `tool_call_relayed` with value-free validation details. `AI_ROUTER_TOOL_CALL_RELAY=false` restores fail-closed validation for every call; capabilities report `profiles.model.tool_call_relay`. Replay of an undeclared call to Antigravity is covered by fixtures only; its acceptance by the live CCA endpoint is unverified. |
| Diagnostics | Structured JSON logs on stderr record every request's shape, admission, dispatch, completion or failure, relayed tool calls, provider latches and catalogue changes, without prompts, arguments or output; see [logging](logging.md). A failed provider call keeps the offending provider output (for example the rejected tool call or invalid JSON) in the memory-only monitor capture, retrievable with `ai-router monitor --detail <request-id>`. |
| Tool choice | `auto`, `none`, `required`, a named function (Chat `{type:"function",function:{name}}`, Responses `{type:"function",name}`) and `allowed_tools` (`mode` `auto` or `required`; Chat nests it under `allowed_tools`) are supported. `none` omits the tool inventory. Named and allowed-tools choices narrow the inventory sent to the provider to the selected tools, so any other returned call fails. When a call is required, visible text is withheld until the result is known, and an answer without a valid call fails with `502 missing_required_tool_call` (`param:"tool_choice"`, `x-should-retry: false`); no call is ever fabricated. Because the text is withheld, a stream normally fails before it commits, as a real HTTP 502; see Streaming errors. OpenAI receives `tool_choice:"required"` over the narrowed `additional_tools` catalogue. Antigravity keeps the reviewed `VALIDATED` calling mode, because CCA support for Gemini `ANY`/`allowedFunctionNames` is unverified, and gets a system instruction to call one of the tools instead. A selected name missing from `tools`, a forcing choice without tools, or a forcing choice combined with a structured output format returns `400 invalid_request` with `param:"tool_choice"`. Custom, hosted and MCP choices stay `unsupported_parameter`. Capabilities report `profiles.model.tool_choice` and each provider's `tool_choice_forcing`. |
| Parallel calls | The gateway may return multiple validated calls when the request permits them. It does not execute tools or promise parallel execution. |
| JSON Schema output | Chat `response_format` and Responses `text.format` schemas are validated locally. Provisional text is withheld until a complete value passes validation. Provider constrained decoding is not promised. |
| History | Typed chronological user, assistant, and tool turns retain original call IDs and results. Private Antigravity reasoning/signature replay is opaque, memory-only, and scoped by client, model, and account generation. |
| Responses item references | Completed items are client-scoped in process memory, with a 24-hour TTL, 1,024 items / 16 MiB per client and 4,096 items / 64 MiB globally. Reasoning references also require the same provider and account generation. Restart clears items. |
| Usage | Prompt, candidate, reasoning, cached, and total counts are mapped where supplied. Missing or inferred usage is marked partial. Responses retain both `agy_usage_partial` and `ai_router_usage_partial` for compatibility. |
| Responses `include` | Only `["reasoning.encrypted_content"]` (or `[]`) is accepted. OpenAI always requests and returns encrypted reasoning items; Antigravity returns no reasoning items, so the hint adds nothing there. Any other value returns `unsupported_parameter`. Chat Completions accepts only an empty `include`. |
| Reasoning controls | Responses `reasoning.effort` and Chat `reasoning_effort` accept `none`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max`. Each request gets one effort decision, made against the served model (after any model fallback), and at most one `X-AI-Router-Reasoning-Effort` value. In order: on Antigravity, `none` and `minimal` mean "no explicit effort", because the model ID fixes it (`ignored`, for exact and fallback-served IDs alike); on a fallback-served Antigravity ID, any other effort that differs from the ID's tier is replaced by that tier (`mapped=<tier>`), because the client chose it for the model it asked for; on OpenAI, `none` or `minimal` is replaced by the lowest listed level above it when the discovered catalogue lists the model's `supported_reasoning_levels` without it (`mapped=<level>`; for `none`, the lowest listed level). Everything else reaches the provider unchanged and carries no header: OpenAI receives `none`, `minimal` and any listed level when the catalogue lists them or lists no levels for the model, and then decides per model, including after a fallback; an exact Antigravity ID whose effort conflicts with its suffix is rejected with `400 invalid_request`. For example, Studio's `gpt-5.4-nano` with effort `none` is served by `gpt-6-luna`; if the catalogue lists `gpt-6-luna` levels without `none`, it receives the lowest listed level with `X-AI-Router-Reasoning-Effort: mapped=<level>`, and otherwise `none` with only `X-AI-Router-Model-Fallback`. With OpenAI unavailable it is served by the Gemini target with `X-AI-Router-Reasoning-Effort: ignored`. Operators should confirm the live ChatGPT catalogue's levels for the fallback target before relying on either path. `reasoning.summary` `auto`, `concise` or `detailed` is accepted because the Vercel AI SDK adds `detailed` whenever an effort is set, but summaries are not produced: reasoning items carry `summary: []`. Requests with a summary receive `X-AI-Router-Reasoning-Summary: unavailable`, and capabilities report the same. Other reasoning fields are rejected. |
| Sampling hints | `temperature` (0 to 2), `top_p` (0 to 1), integer `seed`, and `frequency_penalty`/`presence_penalty` (-2 to 2) are accepted on both APIs. They are range-checked, never forwarded, and have no effect; out-of-range or mistyped values return 400 `invalid_request`. Responses with any of them carry `X-AI-Router-Sampling-Controls: ignored`. Active controls remain `unsupported_parameter`: `n` other than 1, `logit_bias`, `logprobs: true`, `top_logprobs` above 0, and a non-empty `stop`. |
| No-op request fields | Both APIs accept `metadata` (at most 16 string values, 64-byte keys, 512-byte values), `user`, `safety_identifier` and `service_tier` `auto`/`default`; `flex`, `priority` and `scale` return `unsupported_parameter`. Responses also accept `truncation: "auto"` and `stream_options: {"include_obfuscation": false}`. The router never truncates history, so an oversized conversation fails at the provider's context limit instead. None of these reach a provider. Responses echo `metadata` (or `{}`) on the response object, including stream events. `X-AI-Router-Ignored-Fields` lists the accepted fields that had no effect. |
| History replay tolerance | A Responses `reasoning` item without `encrypted_content` cannot be used by either provider; it is dropped and `X-AI-Router-Reasoning-Replay: dropped` is returned. A replayed Responses assistant `refusal` part becomes assistant text, as a Chat `refusal` already does. Chat assistant `annotations` (empty or `url_citation`), assistant `reasoning_content` and content-part `cache_control` are accepted, removed, and named in `X-AI-Router-Ignored-Fields` (empty annotations are not named). |
| Retry guidance | Validation errors (4xx other than 408, 409 and 429), invalid or incomplete output shapes (`invalid_structured_output`, `incomplete_structured_output`, `invalid_provider_tool_call`, `incomplete_provider_output`, `output_limit_exceeded`, `missing_required_tool_call`) and durable provider restrictions return `x-should-retry: false`, so official SDKs do not repeat a paid request. Upstream 401/403 credential rejections are durable too: they become 503 with the provider's explanatory code, so SDKs do not report the router key as wrong, with `x-should-retry: false` and no `retry-after`, because every retry fails until the operator signs in again. `504 provider_timeout` also returns `x-should-retry: false`: each retry would be up to another full request deadline (120 seconds by default) of paid generation that may time out the same way. Other 503s return `retry-after`: 10 seconds for local saturation (`busy`, `shutting_down`), 30 seconds for provider conditions such as OpenAI or Antigravity overload (both 503). An OpenAI overload, transport failure or upstream 401/403/5xx latches the provider until the next catalogue probe (at most 60 seconds while healthy); requests in that window are answered locally and make no upstream call. A latched transient failure replays as 503 with its original code and `retry-after: 30` (a mid-stream `server_error` included); a latched credential failure keeps `x-should-retry: false`. Local queue and body-slot saturation is 503 `busy`, not 429, because n8n never retries 429; the monitor counts it in the busy bucket and records `error_code: busy`. Rate limits stay 429 with `retry-after: 10`. |
| Streaming errors | A stream's HTTP 200, first Chat chunk and `response.created` wait for its first client-visible output: a text delta, a validated tool call or the terminal result, never earlier than the provider's acceptance (its `Init` event, after accepted upstream response headers). Failures before then return the same HTTP status, error body (including `param`) and headers (retry guidance and disclosures) as a nonstreaming request, as on OpenAI. That covers overload, quota, authentication and timeout, and also output that was withheld and then failed: schema validation, or a required tool call that was not made. The wait is bounded at 15 seconds, the keepalive interval; a stream still silent then is committed. Later Responses failures emit the spec `error` event (`code`, `message`, `param`, `sequence_number`, plus a top-level `error` object, which official SDKs and LangChain raise on), then `response.failed`, whose response keeps the text already streamed as a message with `status: "incomplete"`, any calls already delivered, and the echoed `metadata`. Later Chat failures emit a chunk with a top-level `error` object, then `[DONE]`. `param` is the field at fault, or `null`: for example `metadata` for a metadata limit, and `tool_choice` for a provider call outside a narrowed or required tool inventory. |
| Disclosure headers | Once a request passes validation, its disclosures (`X-AI-Router-Reasoning-Effort`, `-Sampling-Controls`, `-Ignored-Fields`, `-Reasoning-Replay`, `-Reasoning-Summary`, `-Prompt-Cache-Controls`, `-Token-Budget-Mode` and Responses `-Item-Storage`) are on every response to it: nonstreaming, streamed, failed before the stream commits, or failed. `X-AI-Router-Model-Fallback` is decided first, so it is also on validation errors. Each header appears at most once. Capabilities list them under `profiles.model.disclosure_headers`. |
| Output budgets | Positive Chat and Responses budgets become best-effort visible-answer guidance. They are not hard output, reasoning, or usage limits. The response header and capabilities disclose this mode. |
| Media | Image, audio, video, and other non-text input are unsupported. |
| Native execution | Removed. `/v1/agy/runs` and all child routes return 404. Only `model` is a valid client-key scope. |
| Conversations | The router does not expose provider conversation IDs or resume a provider-side session. Submit complete history or use supported Responses item references. |

The OpenAI provider remains available when Antigravity is disabled or
restricted, and the reverse is also true. `GET /v1/ready` succeeds when at least
one enabled provider has a ready model. `/v1/models` contains only exact IDs
from currently usable catalogues. Antigravity additionally requires membership
in the 13-ID reviewed baseline; unreviewed image, internal and future SKUs are
withheld until their contracts are reviewed. Previously observed but unavailable IDs
return an actionable provider-unavailable error instead of routing elsewhere:
`503 provider_unavailable`, or the provider's own latched or sign-in reason
(such as `openai_auth_required`) when it has one, with retry guidance. Model
fallback applies only to chat model IDs never observed, and observations
survive restarts, so it cannot hide such an outage. `/v1/capabilities` reports the policy under `profiles.model.model_fallback`,
and monitor request records keep the requested ID beside the served model.

The provider admission limits are independent. `AI_ROUTER_MAX_CONCURRENT` and
`AI_ROUTER_MAX_QUEUE` default to 2 and 8 for Antigravity;
`AI_ROUTER_OPENAI_MAX_CONCURRENT` and `AI_ROUTER_OPENAI_MAX_QUEUE` default to 2
and 8 for OpenAI. Their active and queued ceilings add together. Global body,
pre-authentication, and client-key limits remain shared.

Monitor `startup_ms` measures elapsed time to the provider adapter's `Init`
event, emitted after accepted upstream streaming response headers for both
providers. It includes request setup, queueing, and authentication through that
point; it does not measure local process startup alone. `first_output_ms`
records the first text delta or validated tool call, excluding private
reasoning. Schema buffering can delay client delivery beyond the underlying
provider event. Aggregate timing and token totals combine both providers, while
each request record retains its provider ID.

The monitor retains rejection counters for the current process separately from
stored request history. Counters include every rejection since `started_at` and
reset on restart; the recent rejection history is sampled to at most 30 records
per minute. Range filters change retained-history aggregates but not those
counters. Persisted telemetry contains bounded metadata only. The private
monitor socket can also retrieve up to 100 recent request/response bodies in
memory, each capped at 64 KiB and redacted for known credential fields; those
details are cleared on restart and are not persisted.

## Client setup notes

These follow from the contract above and from the client audit; each is a
deployment choice the router cannot make for the client.

- **Twenty** must use the `@ai-sdk/openai-compatible` package (an
  `AI_PROVIDERS` entry with `npm:"@ai-sdk/openai-compatible"` and the router's
  base URL). With `@ai-sdk/openai`, Twenty adds the hosted `web_search` tool and
  `include:["web_search_call.action.sources"]` to every chat turn, and the
  router rejects both with `400 unsupported_parameter`, so every turn fails.
  The compatible package uses Chat Completions without hosted tools.
- **Cognee and n8n embeddings** must target a separate embeddings service. The
  router has no `/v1/embeddings` (it returns 404), so pointing Cognee's
  `EMBEDDING_ENDPOINT`, or an n8n Embeddings OpenAI node's credential, at the
  router fails Cognee's startup check and cognify, and n8n vector-store
  workflows. Sending an embedding model ID to the chat endpoints returns
  `400 model_not_found` (chat models only), never chat output.
- **n8n** options that remain unsupported and return `400 unsupported_parameter`:
  Chat Model `text.verbosity` `low` or `high` (`medium` is accepted); built-in
  tools (`web_search`, `file_search`, `code_interpreter`); and the OpenAI app
  node's `previousResponseId`, `conversation` and `background` options. Leave
  them unset; send full history instead of a previous response ID.
